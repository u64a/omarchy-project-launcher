# Security

## Reporting a vulnerability

Please report suspected vulnerabilities privately through GitHub's security advisory feature for this repository. Do not open a public issue for an unpatched vulnerability.

## Security model

Omarchy plugins run unsandboxed with the current user's permissions. Project Launcher reads directory entries and hardened Git status output from the configured projects folder, then opens the user's configured CLI or a plain terminal in the selected repository.

Launcher preferences are stored in the user's XDG configuration directory, not in repositories. Setup writes them only after the user presses Save. Custom commands are split into executable arguments without shell interpretation and must use a command on PATH or an absolute executable path. Like the built-in launchers, custom commands run with normal user permissions; only configure commands you trust.

The QML process clears its inherited environment and passes only required identity, locale, XDG/session, SSH-agent, and project-root variables. Helper `PATH` is fixed to `/usr/bin`; loader, Python, shell-startup, and Git control variables are not forwarded. The wrapper and source entry points use isolated `/usr/bin/python`, and system dependencies (`git`, `gio`, `omarchy-menu-select`, `xdg-terminal-exec`, and `env`) are absolute paths. This keeps repository inspection and terminal selection independent of ambient executable lookup.

Built-in and custom launchers are intentionally user-selected programs and may live in user-managed tool directories. Their executable is resolved to an absolute path before changing into the repository. Empty and relative `PATH` components are ignored, closing repository-local lookup after the working-directory transition. The user's filtered absolute-only search path is restored only inside the selected launcher or login shell so tools such as mise-managed CLIs continue to work. A same-user process able to replace an already selected executable or modify trusted user configuration remains outside the plugin's isolation boundary.

At the user's request, it can clone or create repositories, import an existing repository by symlink/move/copy, and move a direct-child project to the desktop Trash. Removal validates that the selected path is directly under the configured projects folder, uses `gio trash` rather than permanent deletion, and requires an additional confirmation for changed or untracked files. Trashing an imported symlink removes only the link, not its external target. The plugin does not require elevated privileges.

## Untrusted repositories

A Git repository carries its own configuration, and several configuration keys make Git execute a command. Status scans therefore run with `core.fsmonitor`, `core.hooksPath`, and the pager disabled.

Those flags do not cover content filters: `git status` runs `filter.<name>.clean` to re-hash modified files, and an in-tree `.gitattributes` cannot be disabled from the command line. A repository is therefore inspected for local configuration before any other Git command runs against it. A repository defining a content filter is reported as untrusted and is never scanned, and importing a repository whose configuration would run commands is refused. Removing a project whose status cannot be verified requires an explicit confirmation, so an untrusted repository can still be cleaned up.

Failed, invalid, timed-out, or oversized configuration inspection fails closed: status and imports are refused rather than interpreting an incomplete scan as an empty list of executable keys. Status parsing and aggregate JSON also fail explicitly at their limits.

Local configuration is enumerated with explicit `--no-includes`. To avoid trusting an incomplete view, **any** local `include.*`, `includeIf.*`, or `extensions.worktreeConfig` key is refused, case-insensitively, even for inactive conditions or a false extension value. This is a conservative compatibility restriction, not an attempt to validate included files. Missing, invalid, or recursive include targets never make a repository trusted.

Only ordinary `.git` directories with non-symlink local configuration are supported. `.git` files (including linked worktrees and separate Git directories), `.git` symlinks, `commondir`, and any `config.worktree` are refused before invoking Git. The latter is refused even when currently disabled, including when worktree configuration could be enabled by trusted global settings. Symlink imports of ordinary repository folders remain supported. These checks apply before status, before import, and again to copied staging trees before publication; cloned configuration is checked before revision lookup/checkout. They do not change Git's trusted user/global configuration or its includes, or the fsmonitor/hooks/pager overrides. Repositories needing these indirections must be handled outside the launcher; do not remove configuration without understanding its effects.

### Lazy fetching and transports

Read-only Git operations are not inherently local-only: a missing object in a partial/promisor repository can cause `git status` or tree inspection to fetch. That fetch can execute repository-supplied `remote.<name>.uploadpack`, select an external helper through `.vcs` or a URL, or initiate network access. A blacklist of one command-bearing setting is not a transport boundary.

All configuration, index, tree, revision, and status inspections use a shared argv builder with the existing hardening plus `-c protocol.allow=never`. The bounded command runner recognizes this prefix and supplies **`GIT_NO_LAZY_FETCH=1` and `GIT_ALLOW_PROTOCOL=""` in a copied child environment**. Git subprocesses inherit the restrictions. `protocol.allow=never` alone is insufficient because protocol-specific policies can override it; the empty environment whitelist denies **every** protocol, including `file`, `ext`, and external remote helpers, regardless of repository/global protocol allowances. As documented in the installed Git manual (`git(1)` environment variables and `git-config(1)` protocol policies), `GIT_ALLOW_PROTOCOL` overrides existing protocol configuration. Regression tests verify the empty-list semantics and command-line/global override resistance on Git 2.55.0, and simulate older Git ignoring `GIT_NO_LAZY_FETCH` while preserving the transport deny. There is no retry with weaker inspection settings.

As a conservative compatibility policy, any local `extensions.partialClone`, `remote.<name>.promisor`, or `remote.<name>.partialCloneFilter` key is rejected case-insensitively before status/import, including false values and repositories currently holding all objects. Copied and cloned configuration gets the same gate before publication/checkout. The error directs users to a complete clone without partial/promisor configuration; deleting such settings does not repair missing objects. Missing-object command failures remain explicit errors, never permission to fetch or report a clean status. The transport boundary also applies when promisor settings come from trusted global configuration rather than the local gate.

Strict import checks additionally refuse `remote.<name>.uploadpack`, `.receivepack`, `.vcs`, and `core.gitProxy` command fields. Ordinary remote URLs are not blacklisted. Explicit user-requested clone permits normal transports and receives the allowlisted session/SSH-agent environment plus trusted user configuration; its subsequent inspection **and checkout** are local-only. The shell process environment is not modified, while helper children use the closed environment described above and launched user programs receive only the filtered absolute search path. This preserves explicit local-path/HTTPS/SSH clones while preventing hidden inspection-time transport. All existing time, output, memory, staging, and checkout file-size budgets remain in force. Injected command runners keep the single-argv contract and must forward inspection argv to `run_command`, which owns both supervision and the child environment.

### Submodules and nested repositories

Top-level configuration checks cannot establish trust in a tracked submodule's own Git configuration. Ordinary superproject status can enter populated submodules and execute their clean filters, including filters hidden behind nested configuration includes or Git-directory redirects.

Submodules are therefore unsupported, not recursively inspected or silently omitted. After the configuration gate, hardened `git ls-files --stage -z` inspects the index without executing filters or entering submodules. **Any mode-`160000` gitlink is refused**, including unpopulated entries and all conflict stages, irrespective of `.gitmodules` or ignore/recursion settings. This gate runs before status and every import method, and again on copied staging trees before publication. A known gitlink produces an explicit unverified status and requires the additional Trash confirmation.

The subsequent status command also uses `--ignore-submodules=all` as defense in depth against index/filesystem changes between checking and scanning. No status command runs before the gitlink gate, and there is only one status invocation per inspection. Clones initially use `--no-checkout --no-recurse-submodules`; because their index is initially empty, bounded `git ls-tree -r -z HEAD` rejects gitlinks before checkout. Checkout explicitly disables submodule recursion, and the resulting index is checked before publication.

Both index/tree commands retain the existing hardening, 15-second command deadline, 1 MiB stdout/64 KiB stderr caps, and 512 MiB per-process address-space limit. NUL-delimited parsing enforces the existing 20,000-record and 16,384-character record-length limits and rejects incomplete or invalid records. Command or limit failures refuse status/import/publication.

Untracked embedded repositories are not recursively status-scanned: Git may recognize their repository metadata, but does not rehash their worktree files through filters. Tests cover direct/included clean filters and fsmonitor commands in such repositories. They remain ordinary untracked entries, and importing their parent does **not** certify nested configuration for later manual use. These checks are not a filesystem snapshot; same-user concurrent modification remains outside the isolation guarantees. Handle repositories requiring submodules in a trusted terminal outside the launcher.

## Availability protections

The exact fixed budgets and cancellation workflow are listed in [README.md](README.md#resource-budgets). Concurrent byte-limited stdout/stderr drains, monotonic command deadlines, bounded enumeration/parsing, and a 512 MiB per-process Git address-space limit prevent unbounded helper captures and scans. QML uses immediate `SplitParser` chunks with an empty delimiter and independent caps/watchdogs; it does not retain arbitrary lines or collect until EOF. A broker/worker arrangement, Linux parent-death signaling, new command sessions, and group termination/reaping cover cancellation and a destroyed overlay without tying the detached terminal to the helper lifecycle.

Copy enforces regular-file byte and filesystem-entry limits during traversal and writing, does not follow source symlinks, and rejects special files. Move is an atomic same-filesystem rename after bounded preflight; cross-filesystem recursive move fallback is disabled. Clone and checkout run in operation-owned staging with live inventory checks and a kernel-enforced per-file size limit. Final inventory and executable-configuration checks precede publication. Cleanup is bounded and never follows staging symlinks or deletes import sources or unrelated destinations.

These are availability guardrails, not an adversarial filesystem or process sandbox. Clone's aggregate byte/entry thresholds can be exceeded between inventory passes; filesystem metadata is additional, and individual Git processes each have their own address-space budget. Use filesystem quotas for a strict aggregate storage guarantee. Filesystems that stall in uninterruptible kernel I/O may outlast user-space deadlines/kill requests; cleanup failures are reported with the operation-owned path. Concurrent modification by another process with the same user's permissions is not isolated. Trusted global Git configuration (subject to inspection transport restrictions), explicit clone's remote authentication helpers, and explicitly launched terminals remain part of the user's normal trust environment.
